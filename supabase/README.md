# 複数端末のリアルタイム共有を有効にする

アプリの公開と、共有DBの準備は別です。コードをデプロイしただけでは共有は始まりません。既存ローカル記録は各ブラウザ内にあり、開発環境からは取得できません。主催者が記録の入った端末で共有グループ（大会）を作成してください。

## 主催者が初回だけ行う設定

1. https://supabase.com/dashboard でアカウントを作成し **New project**。プロジェクト名は `janroku` など。無料プランの組織・近いリージョンを選択し、DBパスワードは自分で安全に保管してください。アプリやチャットには入力しません。
2. プロジェクトの **SQL Editor → New query** で [setup.sql](setup.sql) の全文を貼り付け、**Run**。アプリの「設定 → 端末間の共有 → Supabaseの接続設定」からSQLをコピー・ダウンロードすることもできます。成功したことを確認してください。繰り返し実行しても既存の対局は削除しません。
3. **Authentication → URL Configuration** の **Site URL** を `https://komiki0401.github.io/majan_score/` に設定。同じURLを **Redirect URLs** にも追加します。**Authentication → Sign In / Providers → Email** が有効か確認。メール確認は有効のまま利用してください。メール配信の利用制限はSupabase側の案内を確認してください。
4. **Connect** または **Project Settings → API / API Keys** で **Project URL** と **Publishable key**（`sb_publishable_...`）を確認。旧形式の `anon` keyも対応します。**Secret key / service_role / DBパスワードは使用禁止**です。
5. 記録が保存されている端末で雀録を開き、**設定 → 端末間の共有・リアルタイム同期 → Supabaseの接続設定** に上記2つの公開設定を入力し保存。
6. メールアドレスと8文字以上のパスワードで **新規登録**。確認メールのリンクを開き、必要なら設定画面で **ログイン**。パスワードはSupabase AuthへHTTPSで直接送信され、アプリの設定・ソースには保存しません。
7. **この端末の記録で共有グループを作成**。アップロードする件数を確認して実行。ローカル記録は元のまま残し、クラウドへコピーします。既存の対局日の解釈が他のタイムゾーンで変わらないよう、移行時に対局日を明示的に固定します。
8. **招待リンクを作成 → コピー** して参加者へ送ります。このリンクは公開接続情報と閲覧参加用の招待コードを含みます。信頼できる参加者にだけ送ってください。

## 参加する人

1. 招待リンクを開くと設定画面に接続先と招待コードが入力されます。
2. **接続設定を保存**。自分のメールアドレスで新規登録・メール確認・ログイン。
3. **招待から参加**。以降は同じグループの記録を閲覧できます。入力・編集・削除は主催者のみ可能です。
4. **ダッシュボード**や**対局履歴**へ移動。別端末の更新はRealtime購読で取得し、再接続・画面復帰・15秒ごとの取得でも最新状態を確認します。

## 権限・保存・競合

- Supabase Authのログインが必要。未ログイン者・非メンバーには対局データを公開しません。RLSで制限し、招待テーブルは直接読めません。
- グループ作成者が主催者。グループ名・ルール・招待コードは主催者のみ変更できます。招待参加者は閲覧専用です。参加者登録・対局の入力・編集・削除もDB保存関数で主催者のみに制限します。招待コード更新は今後の新規参加のみ無効化し、既存メンバーの権限は取り消しません。メンバーの追放UIは未実装です。
- 書き込みは検証付きDB関数のみ。点数入力では合計・順位・ウマ・オカ・端数をDBでも再計算します。計算済みポイント入力は手動申告値として検証し、ウマ・オカを再加算しません。
- DBの更新番号で同時編集の上書きを検出。競合時は最新データを取得し、入力内容を残して保存を止めます。最新の対局状態を確認して再度確定してください。自動マージはしません。
- 共有のオフライン書き込み・未送信キューはありません。通信失敗時にローカルへ保存したふりをしません。
- 更新前の共有データをDBの `jr_audit` に記録。参加者がこの監査ログを変更・削除することはできません。アプリ上の修正履歴とは別のサーバー監査です。アプリ内の監査ログ閲覧・復元UIは未実装。
- 1グループの状態上限は2MB、参加者100人、半荘10,000件、1対局の修正履歴1,000件。主催者あたり10グループ。状態全体の更新方式なので、無料DB容量やRealtimeの制限を継続して確認してください。
- ローカル記録は共有に切り替えても保持します。「ローカルの記録に戻る」で元の端末内記録へ戻れます。クラウド更新はローカル記録と自動マージしません。
- 共有接続情報は公開用キーなので、招待リンクに含まれていて構いません。認証トークン・Secret keyは招待リンクには含めません。アクセスを守るのはRLSとメンバー認証です。

## 検証

`npm test` は計算ロジックに加え、PGlite（PostgreSQL）でSQLを実行して非メンバー拒否、権限、サーバー検証、競合、招待更新、変更できない監査ログを検証します。ブラウザの接続テストでは通信応答をシミュレートしています。実SupabaseのRealtime・メール配信・認証設定は、プロジェクト作成後に別途確認が必要です。

実サービス接続後、主催者と参加者の異なる2端末で主催者が1半荘を入力し、双方の履歴に同じ結果が現れること、参加者がルールを変更できないことを確認してください。これを確認するまで共有が有効になったとは判断しないでください。


## 保存するデータ構造

`jr_rooms` の1行が1つの共有大会です。`state`（JSONB）内に大会名・ルール・参加者リスト・半荘リスト・4人のスコア・修正履歴を保持します。既存のReactのモデルと互換性を保ち、1回のDB関数で整合した単位として保存します。`jr_members` は認証ユーザーの閲覧参加、`jr_invites` は閲覧参加用コード、`jr_audit` は変更前のサーバー監査記録です。

RLSのSELECTポリシーはメンバー限定。INSERT/UPDATE/DELETEの直接権限は全クライアントから剥奪し、`jr_save_room` 内で `owner_id = auth.uid()` を要求します。画面のボタンを改変しても参加者には書き込めません。異なる端末から主催者アカウントでログインすれば、主催者は複数端末で入力できます。
