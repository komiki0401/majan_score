# 登録不要の公開大会へ移行する

React + TypeScript + Viteを維持し、SupabaseのDB・Realtimeを使用します。サインイン、新規登録、メール認証、匿名Authアカウントは使用しません。Project URLとPublishable keyのみブラウザへ渡します。

## 1. SQLを適用（新規・旧バージョン共通）

Supabase Dashboard → **SQL Editor → New query** で [setup.sql](setup.sql) の全文を実行してください。アプリの「設定 → クラウド接続設定」から全文のコピー・ダウンロードもできます。

このSQLはトランザクション内で実行し、既存の大会・参加者・半荘・スコア、旧監査テーブルを削除しません。繰り返し実行できます。旧APIの実行権限を取り消し、新しい公開対象限定APIを用意します。テーブルのRLSは有効のままです。

**既存の大会は自動公開しません。** SQL適用直後に大会一覧が空でもデータが消えたわけではありません。

## 2. 既存大会を公開対象に指定

SQL Editorで一覧を確認します。

```sql
select
  id,
  state->>'name' as tournament_name,
  jsonb_array_length(state->'players') as player_count,
  jsonb_array_length(state->'games') as game_count,
  is_public,
  deleted_at
from public.jr_rooms
order by updated_at desc;
```

公開したい大会のIDを、次のSQLのUUIDに置き換えて実行してください。

```sql
select public.jr_publish_existing('ここに大会のUUID'::uuid);
```

この処理はSQL Editorの管理権限でのみ実行できます。ブラウザから未公開の大会を公開することはできません。参加者・既存の点数・順位・ポイント・IDは保持します。古い半荘に番号がない場合のみ、同一日・同一卓の記録順を半荘番号として追加します。旧Authユーザーは既存データとの参照があるため、移行時に削除しないでください。

新たにアプリから作成した大会は公開対象になります。公開大会は誰でも閲覧・入力・編集・ルール変更・削除・復元できます。名前等は公開してよい内容だけにしてください。

## 3. 全端末の接続設定

### A. 通常の公開URLをそのまま配りたい場合（推奨）

GitHubリポジトリ → **Settings → Secrets and variables → Actions → Variables → New repository variable** で、次の公開用変数を登録します。

| 変数名 | 値 |
| --- | --- |
| `VITE_SUPABASE_URL` | `https://あなたのプロジェクト.supabase.co` |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | 公開用Publishable key（`sb_publishable_...`） |

Supabase Dashboard の **Connect / Project Settings → API Keys** から取得できます。**Secret key、service_role、DBパスワードは一切登録しません。** ここで指定する公開用キーはビルドされたブラウザコードに含まれる前提のキーです。

変数の保存後、GitHubの **Actions → Test and deploy to GitHub Pages → Run workflow** を実行して再ビルドします。完了後は `https://komiki0401.github.io/majan_score/` を開くだけで大会一覧が表示されます。フロントエンドに秘密鍵を置く必要はありません。

### B. GitHubの変数を変更せず、すぐに共有したい場合

1. 雀録の **設定 → クラウド接続設定** にProject URLとPublishable keyを保存します。旧バージョンでこの端末に保存した公開用接続設定も再利用します。
2. **大会一覧URLをコピー**して配ります。URLには公開用の接続情報のみを含め、AuthトークンやSecret keyは含めません。
3. 受け取った人はURLを開くだけで大会一覧へ進めます。登録や接続設定の手入力は不要です。
4. 大会ごとのURLも大会カードのコピーボタンから共有できます。

設定画面の接続先は端末内保存なので、Bの方法では、接続情報のない通常のベースURLではなくコピーした共有URLを配ってください。

ローカル開発は `.env.example` を `.env.local` へコピーして公開用の2変数を設定できます。`.env*` はGit追跡対象から除外しています（テンプレートは除く）。

## 4. 使い方

- 大会一覧から大会を選択 → スコア入力へ。
- 参加者を登録 → 点数または計算済みポイントを入力 → 確認 → 保存。
- 点数入力はDB側でも順位・ウマ・オカ・端数を計算し直します。ポイント直接入力は従来どおり手動計算済みの値を保存します。
- 同じ日・卓・半荘番号の二重登録を拒否します。複数卓は卓番号を変えてください。
- 保存後はダッシュボードを表示し、他端末のランキング・順位グラフ・実況コメントも更新されます。
- 履歴の削除前データは「変更履歴・復元」から戻せます。復元も履歴に残ります。
- 大会自体の削除は物理削除ではありません。「削除済みも表示 → 大会を復元」で戻せます。
- 旧ローカル記録はブラウザに保持します。大会一覧の「この端末に保存されている記録」から開く、または公開大会へコピーできます。

## RLS・API・レート制限

- `jr_rooms` の匿名/認証済みクライアントによる直接SELECT/INSERT/UPDATE/DELETEを禁止。専用のSECURITY DEFINER関数が `is_public` を確認して、必要なデータだけ返します。`owner_id` や旧監査ログを公開しません。
- Realtimeには、公開大会のID・更新番号だけを持つ `jr_public_events` を使います。RLSで公開対象だけを購読でき、イベントを受けたら検証APIから最新状態を取得します。旧 `jr_rooms` のRealtime配信は解除します。
- 公開変更履歴 `jr_public_changes` は公開大会の履歴のみSELECT可能。ブラウザからの直接更新・削除は禁止です。履歴には公開後の変更のみを記録し、旧非公開の監査テーブルは公開しません。
- 変更は参加者・半荘・設定単位で比較して適用します。別の半荘への同時入力は両方保持。同じ記録の競合は自動上書きせず、入力を残して再確認を求めます。
- リクエストIDと同一日・卓・半荘番号の両方で、再送や二重タップによる重複を防止します。
- 新規大会作成：全体で毎分3件・UTC日次20件、公開中の大会が100件に達すると新規作成を停止します（既存大会の復元は可能です）。
- 保存・復元：全体で毎分300件・UTC日次10,000件、1大会あたり毎分60件・日次2,000件、端末識別子ごと毎分20件。
- 端末識別子は本人確認ではなく、変更可能な補助情報です。書き換えても大会単位・全体単位の上限を超えられません。無効な操作も書き込み回数にカウントします。
- 1操作256KiB、最大200件の差分。1大会の状態2MiB、参加者100人、半荘10,000件、半荘内の修正履歴1,000件まで。大量の一括削除は分けて行ってください。
- APIはDBの行ロック・権限制御・入力値検証・原子的な変更履歴保存を行います。復元時にも変更後の値と現在値を比較し、他人の新しい編集を消しません。半荘で参照する参加者も削除されている場合は、先に参加者の削除を取り消してから半荘を復元してください。
- クライアントは公開変更履歴の最新100件を表示します。古い履歴はDBに保持しています。管理者はSQL Editorから調査できます。自動削除はしていません。

## 公開運用の限界と管理

公開編集では、意図的な誤入力も有効な操作として受け付けられます。変更履歴と復元はありますが、本人確認や個別利用者の追放はしません。レート制限は大量書き込みを制限する仕組みで、DDoS・Supabaseの読み取り転送量・DB容量を無制限に防げるものではありません。Supabaseの使用量・アラートを確認し、必要ならプロジェクト側のレート制限やWAF等を追加してください。全体上限は端末識別子に依存しませんが、上限が悪用で消費された場合は通常利用も制限されます。

緊急時に特定大会だけを非公開へ戻す場合は、SQL Editorから実行します。

```sql
update public.jr_rooms set is_public = false where id = '対象UUID'::uuid;
```

以降の取得・保存・履歴参照は拒否されますが、既に閲覧・コピーされた情報は回収できません。DBには元の記録を残します。Authはアプリから使用しないため、新規ユーザー作成をSupabase側で無効にしても公開機能に影響しません。既存のAuthユーザー削除はこの移行には不要です。

## テストと実環境確認

`npm test` は実際のPostgreSQLエンジン（PGlite）でSQL移行・匿名権限・非公開対象保護・サーバー再計算・競合・重複防止・履歴復元・レート制限を実行します。ブラウザでも同じSQLを背後に置いたAPIを使って複数コンテキストを検証します。SupabaseのHTTP/WebSocket配信部分はテスト用にシミュレートするため、実プロジェクトのSQL適用後に2台の端末で最終確認してください。

1. 2端末で同じ公開大会を開く（メール・アカウントは不要）。
2. 別々の卓で保存し、双方の記録が残ることを確認。
3. 同じ半荘を同時修正すると競合が出ることを確認。
4. 削除後、変更履歴から復元。
5. どちらかの保存後、もう一方のランキングと実況が更新されることを確認。
