# 短縮共有URL・運営者ダッシュボード

## 公開コードとDB設定は別です

既存のSupabaseプロジェクト、GitHub Pages、保存済み対局を使います。この変更の検証では、本番DBへの書き込み・SQL適用・アカウント作成は行いません。以下の設定はプロジェクト所有者が実施してください。

**追加SQLが未適用の間は、グループ作成は従来の長い編集可能URLを返します。管理画面は情報を取得できません。認証を省略する代替動作はありません。**

## 1. SQLの適用

1. Supabaseの既存プロジェクトを確認し、通常のバックアップを確認します。
2. 既に `groups.sql` が適用されているプロジェクトのSQL Editorで、[service-management.sql](../supabase/service-management.sql) の全文を確認して実行します。今回 `setup.sql` / `groups.sql` を再実行する必要はありません。
3. トランザクション内で、短縮URL対応表、管理者許可表、グループの状態・最終対局更新列、更新トリガー、管理用ビュー・RPCを追加します。既存グループへの短縮ID対応表を追加しますが、既存の名前、編集トークン、対局・スコアは変更しません。グループ数に応じて短時間のDDLロックが発生するため、利用の少ない時間帯を推奨します。
4. 管理者認証を設定するまでは管理RPCは利用できません。

再適用しても既存IDは維持します。将来 `groups.sql` を再適用した場合は、同ファイルがRPCを定義し直すため、**その後に本追加SQLを再適用**してください。既存のRLSを無効化したり、privateスキーマをAPIの公開スキーマに追加しないでください。

## 2. 共有URLと入力権限

- 閲覧用: `https://komiki0401.github.io/majan_score/#/g/<16文字のID>`
- 入力・編集用: 同じURLに `?edit=<既存形式の編集キー>` を付けたフラグメント内リンク。共有設定からコピーできます。
- 従来の `#group=...&room=...` URLも従来どおり編集可能です。新リンクにはSupabase接続情報を含めません。過去に接続情報付きで発行されたURLは互換性のため読み込めます。

短縮IDは96ビットのランダム値（大文字・小文字を区別する16文字）です。6文字では多数グループの推測耐性が不足するため16文字にしています。IDを知るだけなら閲覧のみで、参加者・対局の登録、編集、削除、復元、大会作成はDBで拒否します。閲覧URLも参加者名・成績を読めるため公開SNSへ投稿しないでください。

作成者のブラウザには、プロジェクト・短縮IDごとに編集キーをlocalStorageへ保存します。他端末で入力する仲間には、共有設定の「入力・編集用URL」を別途渡してください。これは従来URLと同じ編集権限を渡す操作です。編集リンクで開くと、保存成功後はアドレス欄から編集キーを除きます。ブラウザ保存不可の場合はキーを含むURLを維持します。設定のキー入力でも編集を有効化できます。

ブラウザデータを消すと記憶した権限は消えます。編集用URLは安全に保管してください。管理画面には編集キーを表示せず、DBにも元の編集キーを保存しないため、運営者の一覧から編集リンクを復元することはできません。キーのローテーション・失効管理は今回の対象外です。

## 3. 運営者の認証設定

一般のグループ利用者にはAuthアカウント不要です。管理者だけ次を設定します。

1. Supabase DashboardのAuthenticationでメール・パスワード認証とTOTP MFAが利用可能か確認してください。既存の認証設定を自動変更しません。
2. AuthenticationのUsersから運営者アカウントを作成し、強い固有のパスワードを設定します。必要なメール確認を完了してください。管理画面に新規登録機能はありません。既存サービスに影響しないことを確認したうえで、不要な公開サインアップを無効にすることも検討してください。
3. Usersに表示される対象ユーザーのUUIDを確認し、SQL Editorで次だけ実行します。メールアドレスやグループIDではありません。

```sql
insert into jr_group_private.admin_users(user_id)
values ('ここをAuthユーザーのUUIDに置き換える')
on conflict do nothing;
```

4. [運営者ダッシュボード](https://komiki0401.github.io/majan_score/#/admin)を開き、メール・パスワードでログインします。
5. 初回は「認証アプリを登録」からQRコードを認証アプリへ登録し、6桁コードで確認します。次回もパスワードと認証アプリが必要です。QRコードは共有しないでください。紛失時はSupabaseプロジェクト所有者がAuthの正式な復旧手順で対応します。未完了の登録が残った場合もAuth側のMFA登録状態を確認してください。

DBの管理RPCは、Supabaseが検証したJWTの `authenticated` / `aal2` と `auth.uid()` の許可表登録を毎回検証します。一般アカウント、AAL1、自己編集できるuser_metadataのadminフラグ、グループ編集キーでは管理情報を取得できません。許可表と対応表にはRLSを有効化し、直接アクセス権限も与えません。

管理セッションはメモリ内だけで、リロード後は再ログインです。ログアウトで取得済み一覧を消去します。フロントエンドに置くのは従来のPublishable Keyのみです。Secret Key / service_role / JWT署名鍵をブラウザ、環境変数 `VITE_*`、GitHubリポジトリへ追加しないでください。

参考: [Supabase MFA](https://supabase.com/docs/guides/auth/auth-mfa)、[RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)。

## 4. 表示する情報の定義

- 発行グループ数: `jr_group_private.groups` の件数。従来のグループ化されていない公開大会は含みません。
- 今月: 日本時間の月初から作成されたグループ。
- アクティブ: 過去30日以内に対局データを更新したグループ。
- 対局数: 現在保存されている対局の合計。論理削除した大会内の対局も含みますが、履歴の各リビジョンは重複カウントしません。対局自体を削除すると減ります。
- 参加人数: 大会をまたいで前後空白を除いた同名をまとめた人数。論理削除大会も運営集計に含みます。
- 最終対局更新: 対局追加・編集・削除・復元で更新。大会名・参加者・ルールだけの変更では更新しません。過去の対局変更履歴も参照し、履歴のない旧インポート対局は大会更新日時を保守的な推定値として表示します。過去の正確な操作日時を捏造しません。
- 状態: 初期値 `active`。今回の状態表示は情報用で、既存の入力権限を変更しません。変更・削除の管理UIはありません。
- 削除候補: 最終対局更新が現在より2暦年以上前。未対局グループは含めません。**自動削除・実行ボタンはありません。** CSVエクスポート・事前告知・未対局グループの扱いを整備してから別途運用を決めてください。

一覧は50件単位のページング、名前検索、削除候補絞り込みに対応します。表示更新は手動です。共有URL欄とコピーは閲覧用だけを返します。

## 5. 検証と未設定時の制限

`npm run verify` はNode24で、既存テスト、短縮経路・ブラウザ権限・管理UIのテスト、一時PGlite DBでのRLS/ACL・他グループ隔離・管理者/MFA判定・候補判定、型チェック、ビルド、秘密鍵パターン検査を行います。SQL再適用時の既存スコア維持も一時DBで確認します。

実Supabaseに対するリリース検査はGETだけで、匿名の直接アクセス拒否・既存公開大会の読み取りを検査します。追加SQLが未適用ならその事実を報告し、従来URLを維持します。これは本番のRLSフラグや全認証ロールのカタログ検査、実管理者でのMFAログイン検査の代わりではありません。

SQL適用・Auth設定後の実アカウントログイン、既存グループの短縮URL発行、新規グループ作成の本番確認は設定完了後に行ってください。今回の自動検証では本番グループ・対局・ユーザーを作成しません。
