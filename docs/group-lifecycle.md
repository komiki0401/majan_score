# 運営者による無効化・復元・完全削除

## 適用するSQL

既存の `groups.sql` と `service-management.sql` が適用済みの同じSupabaseプロジェクトに、[group-lifecycle.sql](../supabase/group-lifecycle.sql) の全文をSQL Editorで適用してください。今回 `setup.sql` / `groups.sql` の再実行は不要です。管理者アカウント・許可リスト・MFAは[既存の設定](service-management.md#3-運営者の認証設定)をそのまま利用します。

このSQLは管理用テーブルとRPC、アクセス判定を追加・更新します。**適用時に既存グループを無効化・削除したり、既存対局を変更する処理はありません。** 今後管理者が明示的に操作したグループだけに作用します。本番へのSQL適用と破壊的操作は自動検証で実行しません。適用前に通常のDBバックアップも確認してください。

新規構築・再適用の順序は `groups.sql` → `service-management.sql` → **`group-lifecycle.sql` を最後**です。前二つがアクセス判定を再定義するため、順序を守ってください。SQL単体を再適用しても既存データ・無効状態・管理履歴は初期化しません。

追加SQL未適用時も通常の雀録と旧管理一覧は維持します。管理操作を押すと設定が必要と表示し、権限検証の省略やフロントエンドだけの無効化は行いません。

## 無効化と復元

1. [管理画面](https://komiki0401.github.io/majan_score/#/admin)でパスワードと認証アプリを使ってログインします。
2. 対象のグループ名・UUIDを確認し、「無効化」を押して確認します。
3. DBの状態が `disabled` になると、旧編集URL・短縮閲覧URL・編集キーのいずれでも情報取得・大会作成・入力・編集・削除・復元ができなくなります。別のグループを新規作成する機能には影響しません。
4. 再開時は同じ行の「復元」を押します。データ、短縮ID、既存の編集キーを変えずに `active` に戻します。再発行や再入力は不要です。

管理者は無効状態でも管理一覧・削除対象確認・バックアップを利用できます。他の運営者が先に状態を変更した場合は操作を拒否し、一覧の更新を求めます。DBのグループ単位ロックにより、進行中の入力処理と無効化・エクスポート・削除を直列化します。

既に端末へ送られたデータ・CSV・画面写真を遠隔消去することはできません。通信中だった読み取り結果も取り消せません。無効化後の新しいAPIアクセスは拒否し、開いたままの画面は次のフォアグラウンド定期確認（通常15秒）または復帰・再読込でアクセス不可画面へ切り替えます。バックグラウンド中は従来どおり定期通信を止めます。

## 完全削除の手順

自動削除はありません。2年以上未更新の表示は確認用であり、削除の許可や実行を意味しません。削除対象が候補外でも管理者は以下の確認を経て手動操作できます。まず対象メンバーへの告知・データ保存の機会を運営者が確認してください。自動告知は未実装です。

1. 対象を**無効化**します。
2. 「バックアップ・完全削除」で対象名・UUID・削除対象件数を確認します。
3. 「削除前のJSONバックアップをダウンロード」を押します。操作中の管理者に結びつく、15分有効の確認記録をDBに発行します。
4. **保存先でファイルを開き**、`format` が `janroku-group-backup-v1`、`snapshot.group.id` が対象IDであること、対局・変更履歴等が含まれていることを確認します。ブラウザがファイル保存を許可したかをサーバーから証明することはできないため、必ず実ファイルを確認してください。
5. 保存確認にチェックし、グループ名とUUIDの両方を正確に入力して「このグループを完全削除する」を押します。
6. 一覧から消えたことを確認します。通信結果が不明なら、再試行より先に一覧更新で状態を確認してください。

DBは毎回、管理者許可表・認証済みJWTのAAL2・無効状態・確認名/ID・バックアップ確認・確認記録の対象/操作者/有効期限・スナップショットのSHA-256一致を検証します。取得後の状態変更、別管理者の確認記録流用、復元を挟んだ古い確認記録、バックアップなしの直接呼出しは拒否します。ブラウザから渡した件数やハッシュだけを信用しません。

## 削除・エクスポートする対象

| 対象 | 内容と範囲 |
| --- | --- |
| `jr_group_private.groups` | 指定UUIDのグループ名・状態・元の編集キーのハッシュ等、1件 |
| `group_links` | 同じグループの短縮URL対応表 |
| `rooms` | 同じ `group_id` の全大会。論理削除済み大会も含む。参加者・ルール・対局・スコア・対局内修正履歴はこのJSON内 |
| `jr_public_changes` | 上記大会IDに属する全変更・復元履歴。100件の画面表示上限を適用しない |
| `jr_public_events` | 上記大会の更新インデックス |
| `jr_public_requests` | 上記大会の再送防止記録。過去の操作データを含む |
| `jr_public_rates` | 上記大会IDが一致する `room-minute:` / `room-day:` / `device:<大会UUID>:` だけ |
| `admin_group_exports` | 当該グループの全バックアップ確認記録。バックアップの対局データではないためJSON本体には入れない |

件数の「対局」は大会JSON内の対局数です。別テーブルとして二重には削除しません。削除は単一トランザクションで実行し、未把握の外部キー等で失敗すれば履歴やリクエストの先行削除も含めすべてロールバックします。スキーマを追加したときは関連表とバックアップ対象を再点検してください。

**残すもの:** 他グループ、`public` スキーマ内の従来大会・ユーザー・監査記録、管理者Authアカウントと許可リスト、グループ共通のレート制限バケット。当該グループの管理操作履歴には対象UUID・操作者UUID・操作日時・件数・元の作成日時を残します。削除済みURLの再利用防止のため、旧短縮IDと編集トークンハッシュのさらにSHA-256を残します。グループ名・参加者・対局内容・元の編集キー/元のハッシュはこの管理履歴には残しません。新しいUUIDで古い編集キーを使った作り直しも拒否します。

バックアップJSONには上記グループデータと取得日時・件数・確認記録IDを含みます。Secret Key / service_role / 管理者セッションは含めません。ただし参加者名、スコア、操作時の端末ID、編集キーのハッシュ等は含むため、運営者が暗号化などで安全に保管し、共有・保管期限も管理してください。ブラウザの永続ストレージにバックアップを保存しません。

## 復元と運営集計

「復元」ボタンは**無効化の取り消し**です。完全削除後のワンクリック復元・JSONアップロードは未実装です。バックアップからの再構築が必要な場合はプロジェクト所有者が内容・依存関係・削除済み識別情報との整合性を確認し、別途承認された復旧作業として行います。汎用的な自動インポートは行わないでください。Supabase側のDBバックアップに過去データが残る期間は、プロジェクト側のバックアップ保持設定に従います。

累計発行グループ数・今月の作成数には完全削除済みの識別記録も含めます。現在の一覧・保存対局数には完全削除済みを含めません。アクティブ数は `active` かつ30日以内に対局更新があるグループです。削除候補は無効グループも含め、最終対局更新から2年以上。未対局は候補に含めず、自動削除しません。

## 検証

`npm run verify` をNode24で実行します。一時PGlite DBで匿名・一般ユーザー・AAL1の拒否、無効化した両URLの全読書き拒否、同じデータ/URLでの復元、バックアップ期限・対象・操作者・変更検出、削除時の全体ロールバック、他グループ/公開大会の維持、削除済みURLの再発行拒否、SQL再適用を検証します。画面テストは確認・ダウンロード・名前とID入力の順序、権限拒否とログアウト後の遅延レスポンスを検証します。

実Supabaseのリリース検査はGETだけです。状態変更・バックアップ確認記録作成・完全削除のRPCは本番テストで呼びません。実環境の特権カタログ検査や本物の管理者MFAログイン確認を自動で行ったと報告しません。
