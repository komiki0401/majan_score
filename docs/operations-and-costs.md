# 多グループ運営・通信量・広告導入メモ

調査日：2026-11-01。今回の変更はフロントエンドのみ。既存DBの変更、SQL再実行、データ追加・削除、広告コードの設置は行わない。

## 通信の調査結果と改善

変更前は次の3経路が独立して15秒ごとに動作していた。

| 経路 | 変更前の定期HTTP取得 | 改善後 |
| --- | --- | --- |
| 大会一覧 | 毎回一覧RPC | 更新番号一覧が変わったときだけ一覧RPC |
| 選択中の大会 | 毎回大会全文RPC＋変更履歴100件 | 更新番号が変わった大会だけ全文・履歴を取得 |
| 全期間集計 | 毎回更新番号一覧。変更大会は別途全文RPC | 上記と更新番号取得・大会全文の処理中リクエストを共有 |

通常のダッシュボード・対局履歴で大会選択中、500大会未満、変更なし、通信成功の場合：

| 状態 | 変更前 | 改善後 |
| --- | ---: | ---: |
| 表示中・15秒あたり | 4リクエスト | 1リクエスト |
| 表示中・1時間あたり | 960 | 240（75%削減） |
| 非表示・オフラインの定期取得 | 動作継続（ブラウザによる間引きはあり） | 0 |

初回取得、手動更新、保存、復帰、エラー再試行、Realtimeによる更新は上記と別。500件以上は更新番号取得がページ数分になる。設定・入力画面では旧構成の全期間集計取得がないので、通常の定期取得は3→1回。非表示になる直前に始まった取得は完了することがある。

更新番号はSupabaseクライアントごとのメモリ内に12秒だけ保持し、同時取得をまとめる。グループ別ヘッダーの異なるクライアント間では共有しない。全文キャッシュは最大200大会で、端末の永続ストレージや共用CDNには新たに保存しない。全期間集計は既存の圧縮した大会別キャッシュを利用する。同一バージョンでは画面のデータを再適用・再集計しない。保存結果は即反映し、古い取得結果で上書きしない。

グループでは表示中15秒周期の確認を維持する。ネットワーク時間・共有キャッシュ・各取得周期のずれにより、他端末の更新の反映は概ね15〜30秒＋通信時間が目安で、厳密なリアルタイム保証ではない。公開大会は既存Realtimeも併用し、全期間集計専用の重複チャンネルを廃止。バックグラウンドでは定期HTTPを停止するが、既存の公開大会用Realtime接続は維持される。複数端末の同時保存は従来のバージョン競合検出・再送IDで保護する。

## 読み取り専用の実測

`node scripts/measure-cloud-reads.mjs` は `.env.local` の公開接続設定を読み、既存公開大会にGETだけを実行する。出力は件数・バイト数のみ。専用グループのURLや内容は出力しない。このコマンドも定期実行せず、必要時だけ使う。

今回の標本：公開5大会、参加者レコード32件（大会間の同名を含む）、対局7件。

| 応答 | UTF-8 JSONサイズ |
| --- | ---: |
| 大会一覧 | 958 B |
| 更新番号一覧 | 568 B |
| 大会全文・平均 | 1,894 B |
| 直近変更履歴・平均 | 3,270 B |
| 変更なし1時間・旧 | 1,605,600 B |
| 変更なし1時間・新 | 136,320 B（約91.5%削減） |

公開データの標本からの算出であり、実際の専用グループの転送量や有料請求額を測定したものではない。TLS・ヘッダー・圧縮・WebSocket・初回表示・保存時の応答は含まない。実際の課金値はSupabase Usageで確認する。

## 100 / 1,000 / 10,000グループの想定

「登録しただけのグループ数」と「毎月利用するグループ数」を分ける。以下は**全グループが月4回、1回2時間、4台で利用＝32端末時間/月/グループ**という仮定。各グループのサイズは上の5大会の標本と同じとし、通常の利用より小さい可能性が高い。

| 毎月利用するグループ数 | 月間定期HTTP・旧→新 | 変更なしJSON通信量・旧→新 |
| ---: | ---: | ---: |
| 100 | 3,072,000→768,000 | 5.14→0.44 GB |
| 1,000 | 30,720,000→7,680,000 | 51.38→4.36 GB |
| 10,000 | 307,200,000→76,800,000 | 513.79→43.62 GB |

上表は変更のない時間の比較であり、無料枠内に収まる保証ではない。例として、月100回の更新を4台に反映し、各更新で一覧958 B＋全文1,894 B＋履歴3,270 B、保存応答1,894 B、月16回の初回読み込み（約14,266 B/台）を追加すると、改善後でも約7.23 MB/月/グループ＝100グループ0.72 GB、1,000グループ7.23 GB、10,000グループ72.3 GBになる。更新番号の定期分は二重計上していない。実際には履歴・大会全文が成長し、その他の通信も増えるため、この標本ベースの計算より余裕を持つ。

同時利用4台/グループの場合、新構成の定期リクエストは100グループ約27件/秒、1,000グループ約267件/秒、10,000グループ約2,667件/秒。CPU共有の無料DBでこの同時負荷に耐えるとは判断できない。これは算術上の到来率であり、本番への負荷試験は実施していない。増加前に隔離したテスト環境でP95応答時間とCPUを測る。

DBは現在の大会スナップショットに加えて変更履歴・再送結果を保持する。仮に100対局/グループ、対局あたり履歴等込み5 KB＋固定50 KBなら約0.55 MB/グループ：100で55 MB、1,000で550 MB、10,000で5.5 GB。インデックスやTOAST等は別で、保存期間でも増える。JSON応答サイズからDB容量を断定しない。自動削除は導入していない。

## 無料枠と運営費

確認時点の[Supabase公式料金](https://supabase.com/pricing)ではFreeは$0/月、DB 500 MB/プロジェクト、通常Egress 5 GB、Cached Egress 5 GB、APIリクエスト数の従量課金なし。通常のDB APIの5 GBにCachedの5 GBを足して10 GBとは扱わない。Proは月$25〜、DB 8 GB、通常Egress 250 GBを含み、超過通常Egressは$0.09/GB。追加計算資源・税・他サービス等は別。契約時に再確認する。

上の変更なし標本だけなら通常Egress 5 GBは旧約3,114端末時間→新約36,678端末時間に相当する。ただし実利用には初回・保存・成長がある。上の更新込み仮定では通信だけで約690稼働グループが5 GBの境界、DB仮定では約900グループで500 MBに近づくため、「無料で1,000グループ運営可能」とは言えない。100グループは検討可能な範囲だが実測監視が必要。10,000稼働グループではPro以上の容量・計算資源とクエリ改善が必要になる可能性が高い。広告収益は掲載率・地域・PV等で変動するので黒字は保証しない。

## 監視と超過前の対策

1. Supabase組織のUsageで期間・プロジェクト・Egress（サービス別）、DB容量、Realtimeを週次確認。日次平均×残日数で月末見込みを計算。自分のプロジェクト以外も組織枠を消費する点を確認する。
2. ProjectのDatabase Reports / Query Performance / AdvisorsでCPU・接続・遅いSQL・呼び出し回数・返却行数、Logs ExplorerのAPIログで頻出パス・失敗率を見る。画面名は変わり得る。請求Egressの正はUsage、ブラウザDevToolsのNetworkは画面ごとの診断に使う。共有HARは専用URLやヘッダーを含むので公開しない。
3. DBは管理者の読み取り専用SQLでサイズを確認：`select pg_size_pretty(pg_database_size(current_database()));`。テーブル別は`pg_total_relation_size`を利用。管理キーをフロント・GitHubに追加しない。
4. 運用目安：通常Egress 3.5 GB/月見込みまたはDB 350 MBで調査、4.25 GB/425 MBで課金移行・容量対策を決定。公式の強制上限ではなく自主的な警戒ライン。
5. 次段階は無操作時の取得間隔延長（更新反映速度との比較）、履歴の必要時取得、グループ別集計スナップショット・対局のページングを検討する。年数分の全JSONを常時転送する方式には限界がある。共有CDNに秘密URL付き応答をキャッシュしない。
6. 有料化時はSpend Capと各項目の対象範囲を確認し、予算・通知を設定する。容量増や履歴の整理にはバックアップと別途承認が必要。今回は削除・移行しない。

参考：[Egressの集計対象・Usage確認方法](https://supabase.com/docs/guides/platform/manage-your-usage/egress)。DB API以外にAuth・Storage・Realtime等もEgressに含まれる。

## DB・アクセス制御・悪用対策の評価

リポジトリのSQL定義を確認した結果：

- `jr_group_private.groups.token_hash`の一意制約、`rooms(group_id,updated_at desc)`、`jr_public_changes(room_id,version desc)`、イベントのroom_id主キーがある。
- グループAPIはトークンのハッシュからスコープを確定し、スコープ付きビューを経由する。更新番号・大会・履歴とも他グループを取得しない。anon/authenticatedへのprivateテーブル権限は剥奪し、限定RPCのみ許可する既存設計を維持。
- `jr_group_index`はグループの大会とイベントをJOINしてroom_id順で最大500件ずつ返す。全グループの全大会をブラウザに取得する方式ではない。全期間集計は自グループの全履歴を対象にするので、1グループ内の大量大会には別の改善が必要。
- 実DBのインデックス利用・RLSカタログは管理者接続なしでは確認していない。公開前検証はGETで無権限アクセス拒否を確認し、RLS/ACL・グループ間分離・競合は一時PGliteのテストで検証する。これを本番カタログ監査とは呼ばない。
- 次の管理者調査では、実データに近いステージングで`EXPLAIN (ANALYZE, BUFFERS)`を使ってJOIN・並べ替え・OFFSET・履歴取得を確認する。必要なら`rooms(group_id,id)`等の候補を比較。全文JSONの返却コストも含めて調査し、根拠のないインデックス追加はしない。今回はDDL変更なし。

現在のサーバー側レート制限はグループ作成が全体3件/分・100件/日、グループ内の大会作成が全体3件/分・20件/日。書き込みはグループ用エンジン全体300回/分・10,000回/日、さらに大会・端末別制限がある。公開大会用エンジンのカウンターとは別。再送IDで重複作成を防ぐ。これらは既存の防御だが、攻撃者が全体枠を使い切ると正常利用者も作成できない。10,000グループを短期間に開設する運用や、多数グループの大会作成には現在の上限自体が制約になる。

拡大時はサーバー側で検証したIP/利用者別制限、CAPTCHA（例：Turnstile）、WAF/Edge Function経由の作成APIを設計し、直接RPCで迂回できないよう権限を切り替えてから上限を見直す。公開キーは誰でも使えるため、クライアント側の待ち時間だけでは防御にならない。IP・CAPTCHA連携にはプライバシー説明とDB/API権限変更の別途確認が必要。今回、制限緩和やログイン追加はしない。

## 広告導入の準備（コード未実装）

候補は、公開ランディングページの説明下、または公開ランキングを読み終えた位置の固定スペース。広告と明示して先に高さを確保し、スマホでナビゲーション・大会選択・保存ボタンと十分離す。スコア入力・編集・確認・共有URL作成フォームには広告を置かない。画面下固定広告や操作中のレイアウト移動、自動全面広告は避ける。[Googleの配置ポリシー](https://support.google.com/adsense/answer/1346295?hl=en)も誤クリックを誘発するボタン等との近接を問題としている。

**専用グループ画面への広告導入は別設計が必要。** `#group=...` は閲覧・操作の権限そのもので、同じページで実行する第三者JSはURLフラグメントや画面データを読める。HTTP Refererにフラグメントが送られないだけでは保護にならない。広告/解析コードには専用URL・参加者名・対局情報を渡さない。まず秘密URLを持たない公開ページだけを対象にする。グループ画面で掲載するならトークンをURLから分離した認可方式や別オリジンの分離を検討し、広告ベンダーの対応可否を含め再評価する。通常のAdSenseスクリプトを単に貼ることやCSPの許可追加では解決しない。

公開前に運営者・連絡先、保存する名前/スコア/日時、URL所持者のアクセス範囲、Supabase等の送信先と保存、保存期間、削除依頼、localStorage/sessionStorageの用途を明示したプライバシーポリシーを整備する。Cookie/広告ID・第三者提供・国外移転等の説明と、適用地域に応じた同意・撤回方法を専門家と確認する。GoogleはEEA・英国・スイスへのパーソナライズ広告で認定CMP/TCFを要求しているため、対象地域を含むならその条件を満たしてから配信する。[Google CMP要件](https://support.google.com/adsense/answer/13554116?hl=en)、[同意設定](https://support.google.com/adsense/answer/7670013?hl=en)。審査・ads.txt・表示内容とPublisher Policiesへの適合も導入時に確認する。

収益サービス化前にはホスティングも再検討する。[GitHub Pagesの制限](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)では、オンライン事業や商用SaaSを主目的にした無料ホスティング利用に制限がある。広告があるだけで一律禁止と断定はしないが、想定する運営形態の適合性を確認し、必要なら商用利用に合うホストと独自ドメインへ移す。今回は既存Pagesでの公開を維持する。
